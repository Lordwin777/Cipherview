1. Executive Abstract

In the modern hyper-connected digital ecosystem, document sharing has become synonymous with centralized surveillance and data harvesting. Conventional sharing mechanisms—including cloud storage drives (Google Drive, Dropbox), social messaging applications (WhatsApp, Telegram), and traditional email—unconditionally require personal identifiable information (PII) before transmission can occur. Users must register phone numbers, email addresses, or corporate accounts, surrendering anonymity and exposing unencrypted metadata to cloud servers.

CipherView fundamentally revolutionizes peer-to-peer document exchange by introducing an uncompromising serverless, local-first secure document-sharing paradigm for Android. By treating identity purely as a self-selected, locally mutable nickname, CipherView eliminates user accounts, passwords, centralized databases, and cloud relays. Sensitive PDF documents are encrypted client-side using AES-256-GCM with 100,000 PBKDF2 key derivation iterations, bundled into a proprietary .cview binary package, and streamed directly over local Wi-Fi or Bluetooth sockets.

[PAGE 2] Philosophy of Serverless Privacy & Threat Modeling

1. The Philosophy of Nickname-Only Identity

Traditional cybersecurity frameworks rely heavily on authentication models based on centralized identity providers (IdPs). While suitable for enterprise cloud architectures, this model is inherently hostile to personal privacy. A physician transmitting a patient report to an on-site specialist does not need a Gmail account; two investigative journalists conferring in an airport do not need a phone number.

CipherView operates on the principle that your identity is simply your chosen nickname. There are no registration wizards, no password recovery mechanisms, and no verification SMS messages. The user chooses an ephemeral nickname (e.g. "Void" or "Sam"), which is stored strictly within the local hardware-encrypted preferences. When nicknames change, CipherView's historical snapshot preservation engine ensures that past audit logs maintain evidentiary accuracy without retroactively modifying historical interactions.

2. Comprehensive Adversarial Threat Model

CipherView was designed to withstand realistic adversarial vectors present in public, semi-trusted, and hostile environments:

Threat Vector 1: Man-in-the-Middle (MitM) Packet Sniffing

Scenario: An adversary operates a rogue Wi-Fi access point or uses promiscuous network sniffing tools (e.g., Wireshark) on a public cafe network.
Mitigation: Document payloads never transit unencrypted. Payloads are encrypted client-side using AES-256-GCM with a key derived from a 6-character Access Code exchanged out-of-band or via an optical QR scan. The network attacker intercepts only high-entropy ciphertext. Any attempt to tamper with packets causes an immediate GCM authentication tag mismatch (AEADBadTagException), cleanly terminating the connection.

Threat Vector 2: Centralized Storage Breaches & Subpoena Exposure

Scenario: Cloud storage providers are compromised via credential theft, zero-day vulnerabilities, or compelled by governmental subpoenas to yield stored data.
Mitigation: CipherView has no cloud storage, no servers, and no relays. Transmitted packets travel directly from sender IP to receiver IP via local TCP sockets. Once transmission completes, no copy exists outside the physical devices.

Threat Vector 3: Unauthorized Digital Screen Extraction

Scenario: A malicious recipient or background spyware attempts to screenshot the decrypted document or capture the screen buffer.
Mitigation: The ProtectedViewerScreen enforces FLAG_SECURE at the Android Window Manager level. The Android SurfaceFlinger compositor blanks the window during system screen captures, screen recording sessions, and task-switcher thumbnail generation.

Threat Vector 4: Analog Capture & Secondary Re-Photography

Scenario: A recipient uses a physical external camera to photograph the smartphone display showing the sensitive document.
Mitigation: CipherView renders a persistent, diagonal, semi-transparent Dynamic Forensic Watermark across every rendered PDF page, embedding the viewer's current nickname, device fingerprint, and access timestamp.

[PAGE 4] Cryptographic Engine & Binary Package Format

1. Mathematical Cryptographic Specification

CipherView's cryptographic pipeline strictly fulfills commercial national security standards:

  • Key Derivation Function: PBKDF2WithHmacSHA256 configured for 100,000 iterations over a 16-byte random salt generated by java.security.SecureRandom.
  • Symmetric Encryption: AES/GCM/NoPadding with a 256-bit key length and a 96-bit (12-byte) initialization vector (IV).
  • Associated Authenticated Data (AAD): The metadata string "${fileName}|${senderNickname}|${expiresAt}|${maxViews}" is fed into cipher.updateAAD() prior to encryption. This cryptographically links the header parameters to the ciphertext: any unauthorized modification of expiry dates or file names will cause decryption to fail.

2. Custom .cview Binary Container Specification

Rather than relying on fragile sidecar metadata files, CipherView bundles ciphertext, salt, IV, and authenticated metadata into a single self-contained binary file:

Byte Offset Field Identifier Size / Type Description
0x00 .. 0x05 MAGIC_BYTES 6 Bytes (CVIEW\x01) Identifies valid CipherView encrypted bundle format
0x06 .. 0x15 Salt 16 Bytes Binary Random cryptographic salt for PBKDF2 key derivation
0x16 .. 0x21 IV 12 Bytes Binary Random initialization vector for AES-GCM mode
0x22 .. 0x29 ExpiresAt 8 Bytes (Long, ms) Epoch timestamp after which document cannot be decrypted
0x2A .. 0x2D MaxViews 4 Bytes (Int) Maximum view limit allowed by sender (-1 if unlimited)
0x2E .. 0x?? FileName 2B Length + UTF-8 Original document name (e.g. contract.pdf)
0x?? .. 0x?? SenderNickname 2B Length + UTF-8 Nickname of the sender at the moment of encryption
0x?? .. EOF Payload + Tag 4B Size + Binary AES-256-GCM ciphertext + 16-byte authentication tag

3. Unambiguous 6-Character Access Code Design

To prevent user entry confusion, CipherView excludes ambiguous visual characters:

Alphabet: { 2, 3, 4, 5, 6, 7, 8, 9, A, B, C, D, E, F, G, H, J, K, M, N, P, Q, R, S, T, U, V, W, X, Y, Z } Total Combinations = 30^6 = 729,000,000 unique keys Omitted Glyphs : '0', 'O', '1', 'I', 'L' (zero, uppercase O, one, uppercase I, lowercase L)

[PAGE 5] Peer-to-Peer Network Transport Engine

1. Dual-Path Connection Architecture

CipherView guarantees peer-to-peer transmission across diverse real-world Wi-Fi topologies by implementing a dual-path discovery mechanism:

Path A: Network Service Discovery (mDNS / NSD)

When entering the Receive screen, the app initializes a local TCP ServerSocket on port 8998 and registers a network service (_cipherview._tcp) broadcasting the recipient's nickname. Sender devices on the same subnet detect this broadcast automatically using Android's NsdManager, enabling zero-configuration one-tap transfers.

Path B: Direct Endpoint QR (Client Isolation Bypass)

In corporate, university, or public hotel Wi-Fi environments, Access Point (AP) Client Isolation blocks multicast DNS packets. CipherView resolves this by displaying a **Direct Network Endpoint QR Code** on the receiver's screen encoding:

cview://192.168.31.170:8998/Sam

The sender points their camera at the receiver's screen using the "Scan Recipient's Screen QR" action. CipherView extracts the target IP and port directly, opening a raw TCP socket and bypassing mDNS entirely.

2. High-Efficiency Binary Socket Streaming Protocol

Socket communication uses optimized 64 KB buffers with interactive transfer progress callbacks:

// Sender Streaming Pipeline Socket(ipAddress, port).use { socket -> socket.soTimeout = 30000 val dos = DataOutputStream(socket.getOutputStream()) dos.writeLong(packageBytes.size.toLong()) // Pre-announce payload length val buffer = ByteArray(65536) var sent = 0L while (sent < total) { val remaining = (total - sent).toInt() val toWrite = Math.min(65536, remaining) dos.write(packageBytes, sent.toInt(), toWrite) sent += toWrite updateProgress(sent, total) } dos.flush() val ack = dis.readByte() // Wait for ACK (0x01 = Verified, 0x00 = Fail) }

[PAGE 6] Android Keystore HSM & Historical Nicknames

1. Hardware-Backed Keystore Integration

All local metadata stored on the device—including document activity history, view counts, and recipient logs—is encrypted at rest using the Android Keystore Provider:

val keyGenerator = KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore") val keyGenSpec = KeyGenParameterSpec.Builder( "cipherview_master_key", KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT ) .setBlockModes(KeyProperties.BLOCK_MODE_GCM) .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE) .setKeySize(256) .build() keyGenerator.init(keyGenSpec) keyGenerator.generateKey()

The master key is generated and stored inside the device's Hardware Security Module (HSM) / StrongBox Keymaster. The raw master key never enters volatile system RAM, rendering metadata unextractable even if physical device storage is inspected.

2. The Historical Nickname Preservation Engine

A persistent problem in nickname-only systems is audit-trail corruption when a user updates their pseudonym. CipherView solves this by decoupling the historical snapshot from the live identity pointer:

Record Field Immutability Policy Behavior Across Identity Changes
sharedByNickname Immutable Snapshot Preserves the nickname active at the exact moment of encryption.
currentSenderNickname Dynamic Pointer Updates when the local sender changes nickname to show identity evolution.
accessHistory Append-Only Log Each log entry freezes the acting nickname at that specific timestamp.

[PAGE 7] Capture-Resistant Viewing Experience

1. OS-Level Screen Capture Prevention (FLAG_SECURE)

When displaying decrypted documents, the viewer activates Android's Window Manager security flag:

window.setFlags( WindowManager.LayoutParams.FLAG_SECURE, WindowManager.LayoutParams.FLAG_SECURE )

This flag triggers four critical system-level protections enforced by the Android SurfaceFlinger compositor:

  • Hardware Screenshot Block: Key combinations (Power + Volume Down) are blocked by the OS with an error toast.
  • Screen Recording Prevention: Third-party screen recording apps capture only black frames.
  • Task Switcher Masking: Swiping up to the recent apps carousel masks the window thumbnail with a solid black privacy shield.
  • External Display Blanking: HDMI projectors and Miracast wireless displays receive a black screen.

2. Dynamic Anti-Leak Watermark Engine

To deter recipients from using a secondary physical camera to photograph the display, CipherView overlays an unremovable, semi-transparent diagonal watermark across all rendered PDF pages:

Canvas(modifier = Modifier.fillMaxSize()) { rotate(-35f) { val watermark = "$viewerNickname • $deviceId • CONFIDENTIAL" // Draws repeated diagonal watermark grid across screen bounds for (x in -size.width.toInt()..size.width.toInt() * 2 step 300) { for (y in -size.height.toInt()..size.height.toInt() * 2 step 150) { drawContext.canvas.nativeCanvas.drawText(watermark, x.toFloat(), y.toFloat(), paint) } } } }

3. Ephemeral In-Memory Lifecycle

Decrypted PDF bytes exist strictly in volatile RAM memory during the active session. When the user taps Close or presses the system back button:

  1. The active PdfRenderer and its file descriptors are immediately closed.
  2. Temporary cache files in private storage are overwritten with zeroes and unlinked.
  3. Rendered page bitmaps are explicitly recycled via Bitmap.recycle().

3. Resolved Real-World Edge Cases

During physical device testing, we successfully resolved the "Corrupted or invalid CipherView package format" issue:

  • Input Sanitization: Files imported via the file picker are now pre-validated before vault insertion. Selecting an image or unencrypted PDF displays an informative warning instead of corrupting the vault.
  • Automatic Vault Pruning: The startup sequence automatically cleans up any legacy non-.cview files from device vaults.
  • Samsung Crypto Provider Fallback: Fixed Conscrypt exception handling so incorrect access codes return InvalidAccessCodeOrCorrupted instead of a format error.
